# PLAN-001：EPlayer 1.0 開發計劃

日期：2026-10-22  
狀態：COMPLETE — 本機 1.0 已交付，限制依使用者同意列明  
先讀：[PR-001 產品需求](PR-001-EPlayer.md)

驗收調整：使用者免除 Windows 10 實機測試，指定後續全部背景測試、耐久測試 10 分鐘；並接受實體媒體鍵、多螢幕／DPI、遊戲覆蓋、尚未完整實測的系統匣／穿透列為已知限制後交付。Windows 10／11 x64 相容目標保留；未實測不能寫成通過。

## 1. 計劃目標與執行規則

以 Rust 建立效能優先的 Windows 本機免安裝播放器，分階段完成 PR 的 F01–F16。使用者已於規劃後授權開始實作；詳細證據及剩餘工作見 [WORK-LOG](WORK-LOG.md)。沒有啟動伺服器或實作 YouTube。

每次只啟動一個 target，完成該 target 的驗證並記錄結果後再進入下一個。執行者為後續獲授權開始實作的開發者／代理；產品範圍變更由使用者決定。階段編號是交付順序，不是工期承諾。

## 2. 現況

- 已建立 Rust 專案、鎖定依賴、完成本機功能整合並產生第一份候選免安裝套件。
- 1.0 release 建置、14 個單元測試、clippy 與格式檢查通過；格式、控制、索引與 DSP 的詳細證據見 WORK-LOG。正式版 600 秒耐久測試與 326 個套件檔案一致性檢查通過。
- 需求已足以進入規劃；技術選型由使用者授權依效能決定。
- 音訊頻譜採柱狀圖；等化器規劃為常見的 10 段加前級增益。這些是可調整的實作決策，不是聲稱使用者指定過頻段數或外觀細節。

## 3. 技術選型

| 部分 | 選擇 | 理由及驗證限制 |
|---|---|---|
| 語言與目標 | Rust stable，Windows x64 MSVC | UI 與核心皆使用 Rust；實作開始才鎖定依賴版本及工具鏈。 |
| 桌面 UI | egui／eframe 原生視窗 | 適合自訂緊湊播放器，eframe 支援原生多視窗；沒有 WebView 執行環境需求。採事件驅動重繪與清單虛擬化；不能僅憑框架名稱宣稱效能較佳，T1 必須實測。 |
| 音訊解碼 | Symphonia 為主要解碼器 | 支援常見編碼與 gapless 相關能力；依 PR 格式矩陣測試，不能將容器支援等同所有編碼皆支援。 |
| 格式補充 | 必要時隨附 FFmpeg | 僅對主要解碼器無法涵蓋的必要樣本使用；T1 查明 AAC 變體／Opus 等實際覆蓋範圍，再決定套件內容；保留完整播放與 seek 驗收。 |
| 音訊輸出 | CPAL，Windows WASAPI | 明確分離解碼與即時輸出；1.0 以一般共享輸出為主。 |
| 音訊處理 | Rust DSP；RustFFT 頻譜 | 等化器、音量與頻譜分析獨立分工；頻譜不進入即時輸出關鍵路徑。 |
| Windows 整合 | windows crate／Win32，必要的系統匣封裝 | 置頂、透明度、穿透、快捷鍵、媒體鍵及系統匣；先驗證 eframe 視窗與 Win32 設定相容性。 |
| 本機儲存 | SQLite 音樂庫／清單，設定檔保存 UI 設定 | 分頁查詢與背景掃描；資料放入免安裝 `data` 目錄。 |
| 封裝 | ZIP：執行檔、必要執行依賴、使用說明及授權清單 | 目標機器不需另行建置；僅附帶當期確有需要的工具。 |

選型依據：egui 的[原生多視窗文件](https://github.com/emilk/egui/blob/main/crates/egui/src/viewport.rs)與[重繪 API](https://docs.rs/egui/latest/egui/struct.Context.html)、[Symphonia 官方專案](https://github.com/pdeljanov/Symphonia)、[CPAL 官方專案](https://github.com/RustAudio/cpal)。上述選擇是本計劃的工程判斷，並非已完成的效能比較。

置頂與透明／穿透行為依據 Microsoft 的 [SetWindowPos](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-setwindowpos) 與 [Window Features](https://learn.microsoft.com/en-us/windows/win32/winmsg/window-features)。一般視窗的 topmost 能力不能作為所有獨佔全螢幕遊戲都可覆蓋的保證，必須以實測報告呈現。

## 4. 執行與資料流

音訊路徑：本機檔案 → 解封裝／解碼 → 重採樣與聲道轉換（需要時）→ EQ／音量 → 有界音訊緩衝 → CPAL 輸出。

背景解碼工作負責磁碟讀取與下一首預讀；音訊 callback 只讀取已準備好的樣本，不執行檔案 I/O、資料庫、FFT、配置大量記憶體或等待 UI 鎖。命令透過佇列傳遞；切歌／seek 使用世代識別，避免舊緩衝繼續出聲。

頻譜取得播放路徑的樣本快照，在獨立分析工作計算；分析來不及時丟棄舊快照，不拖慢音訊。UI 只讀最新結果。播放時鐘以已消耗／輸出的音訊樣本及可用裝置時間為基準，不能以 UI 計時器累計歌詞時間。

主視窗、迷你播放器與歌詞視窗共用播放狀態。掃描、metadata、封面處理與儲存由背景工作處理；UI 請求設定變更，不直接執行大量磁碟操作。

無縫播放需同時處理解碼器延遲／padding、下一首預讀、重採樣狀態與輸出連續性；來源本身的靜音不能誤當成解碼 padding 去除。不以跨曲淡入淡出代替無縫播放。

## 6. Target 詳細工作

### T1：技術路徑與資源基準

目標：在投入完整 UI 前確認音訊、原生多視窗與必要格式可行。

範圍：檢查開發環境與可用測試機；最小 eframe 視窗、CPAL 播放及第二個透明置頂視窗；建立合法取得或自行生成的音訊樣本矩陣；驗證主要解碼器與必要 fallback；測試下一首預讀路徑。

驗證：記錄 CPU／GPU／記憶體、播放 underrun、裝置／驅動、OS build；試驗兩個浮動視窗同時存在、主視窗隱藏、透明度與穿透恢復；記錄全螢幕相容性。此階段試驗只在使用者授權開始實作後執行。

完成條件：選型可支援必需功能，或有具體失敗證據與替代建議；格式覆蓋與包裝依賴清楚；建立可重複的效能基準與後續預算。不得以「套件說有支援」代替跑樣本。

不做：完整介面、伺服器、YouTube 研究或工具整合。若必要能力失敗，先更新選型與 plan；涉及縮減需求時詢問使用者。

### T2：可用的本機播放器

目標：完成最小但可靠的本機聆聽流程。

範圍：開檔、解碼、音訊輸出、重採樣、基本控制、播放佇列、循環／隨機；深淺主題與緊湊主視窗；載入及錯誤狀態。保留下一首預讀能力，完整 gapless 驗收在 T5。

驗證：格式矩陣、連續快速切歌／seek、長檔案、中文檔名、損壞檔案、裝置不可用及拔除；播放與 UI 不應互相阻塞。

完成條件：F01–F04 與 F12 的當期流程可操作，有自動化狀態轉換測試及人工聆聽／畫面證據。

不做：YouTube、線上歌詞、尚未進入階段的進階 UI。

### T3：音樂庫與清單保存

目標：可以管理及重新開啟自己的音樂收藏。

範圍：指定資料夾掃描、metadata／封面讀取、搜尋、播放清單編輯與儲存；掃描重複／遺失檔案處理；本機資料目錄與設定保存。

驗證：至少 10,000 筆索引的列表／搜尋操作，對應磁碟樣本掃描時保持播放；重複掃描不產生重複索引；重新開啟可還原；缺少封面、檔案搬移、不可寫資料夾都有可理解行為。

完成條件：F05–F07 通過；長列表只繪製可見項目，記憶體不隨反覆掃描無限增長。

不做：寫回音樂標籤、刪除來源檔案、雲端同步或音樂下載。

### T4：浮動模式、歌詞及 Windows 控制

目標：在使用其他程式時仍可看歌詞並控制播放。

範圍：完整／精簡浮動 preset、獨立 LRC 視窗、置頂、拖曳、縮放、透明度、穿透；系統匣、快捷鍵及媒體鍵；狀態與配置同步。穿透必須具備可用的退出途徑。

驗證：100%／150%／200% DPI、多螢幕搬移／拔除、主視窗隱藏；浮動視窗不意外搶焦點；快捷鍵被占用時安全處理；LRC 缺失、不同編碼、offset、seek 與暫停同步；各模式保存截圖。分別記錄遊戲三種顯示模式下的結果。

完成條件：F08、F11、F13、F14 通過；獨立歌詞與迷你播放器可同時存在；穿透不會把使用者鎖在不可操作狀態。

不做：遊戲注入、強制覆蓋所有獨佔全螢幕遊戲、網路歌詞搜尋。

### T5：EQ、無縫播放與頻譜

目標：完成已確認的進階本機音訊能力。

範圍：10 段 EQ、前級增益與 bypass；參數平滑及必要的輸出範圍處理；精確曲目邊界、下一首預讀；FFT 頻譜柱狀圖與持久化開關。頻譜規劃更新上限 30 Hz，隱藏或停用時停止分析；此數值屬初始工程設定。

驗證：正弦／掃頻訊號檢查 EQ 頻率響應；bypass 不改變訊號；以連續訊號分割成兩首檢查無縫接合，包含有 padding metadata 的有損樣本；不同採樣率／聲道曲目切換需驗證重採樣後的連續性。使用已知頻率檢查頻譜位置；關閉後分析計數停止並比較資源使用。

完成條件：F09、F10、F15 有訊號層級證據及人工播放確認；頻譜不以犧牲輸出穩定性維持動畫；缺少可靠邊界 metadata 的來源限制有紀錄。

不做：跨曲淡入淡出、多種動畫主題、音訊錄製、麥克風分析或 YouTube。

### T6：1.0 驗收與免安裝交付

目標：將功能完整版本整理成可直接使用的本機套件。

範圍：整合回歸、效能分析與修正、ZIP 封裝、必要執行依賴及授權資訊、操作說明、相容性表；確認套件不含開發環境路徑或非必要工具。

驗證：在無 Rust 工具鏈、無額外解碼器且斷網的乾淨 Windows 10／11 x64 環境解壓執行；一般權限；路徑含中文／空白；10 分鐘混合格式播放（2026-10-23 使用者調整），期間操作掃描、切歌、overlay 和頻譜；對照全部 F01–F16。

完成條件：輸出 release ZIP、測試結果、效能數據、操作文件及已知限制；必需項失敗時不標記 1.0 完成。全螢幕遊戲依 PR 的盡力相容範圍驗收。

不做：安裝程式、自動更新、YouTube 相關功能。

## 7. 整體驗證與效能紀錄

每次實質修改後執行 `cargo fmt --check`、`cargo clippy --all-targets -- -D warnings`、`cargo test` 及 `cargo build --release`。本機使用 scripts/cargo.ps1 與已快取依賴；檢查結果記入 WORK-LOG。

有意義的自動化測試集中於播放狀態轉換、seek 後舊音訊失效、清單保存、LRC 時間對應、DSP 與曲目邊界；Windows 視窗行為及聽感需人工驗證，不用純單元測試取代。

效能測量需固定並記錄硬體、OS、音訊裝置、音樂庫大小、音訊格式、視窗大小／DPI、工具版本及取樣時間。場景包括閒置、一般播放、掃描期間播放、完整 overlay＋歌詞、頻譜開／關及全部視窗隱藏。

記錄 CPU 平均／峰值、GPU 使用、工作集／私有記憶體、啟動時間、控制回應延遲、underrun 次數、各視窗重繪及頻譜分析次數。T1 建立數字預算，T6 按同一條件比較；硬性要求是正常測試負載下不因 UI 造成音訊 underrun、停用頻譜後不再分析、隱藏視窗無持續動畫，10 分鐘測試無持續性記憶體增長。

## 8. 風險與處理

| 風險 | 處理／決策點 |
|---|---|
| egui 重繪或多透明視窗造成高資源使用 | T1 先量測，採按需更新與隱藏節流；無法滿足需求時先記錄替代框架評估，不直接重寫完整產品。 |
| 同副檔名內含不同編碼 | 依樣本矩陣驗證，必要時補充解碼工具；在包裝文件明列支援範圍。 |
| Gapless 依賴來源 metadata 與輸出路徑 | 使用已知連續訊號測試；分開記錄來源限制與播放器缺陷。 |
| Overlay 在部分遊戲不可見 | 分類記錄實測結果，優先正常桌面與無邊框模式；不擴大為遊戲 hook 專案。 |
| 外部工具／CRT 缺失 | 在乾淨系統驗收隨附依賴，確認必要授權與再散布檔案完整。 |
| 音樂庫掃描與視覺化搶占資源 | 有界佇列、背景工作、快照可丟棄、封面快取限額，音訊輸出最高優先。 |

## 9. 1.0 之後與下一步

1.0 完成後另立需求／計劃處理 Y01–Y04：YouTube 網址與播放清單、搜尋、混合播放清單、只播音訊。此處僅保存已確認範圍，不開始研究或建置 YouTube 架構。

目前結果：1.0 正式版完成 600 秒背景耐久測試、回歸及免安裝封裝核對。依使用者 2026-10-23 指示，所有新測試均在背景執行，不操作桌面、不搶焦點；無法由背景測試驗證的視窗行為保留未驗證狀態，不以單元測試冒充實測。既有失敗／中斷報告保留，不與新一輪混算。
